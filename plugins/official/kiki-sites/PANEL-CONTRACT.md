# Sites panel contract (v1)

UI owner writes `panel.html` (and optional `panel.js`, `panel.css`) in this package. Logic owner supplies `entry.mjs` and `lib/`. Manifest panel id is `sites`, slot `workspace`. Use the existing `kiki.panel.v1` iframe bridge, `method: 'plugin.call'`, with an integer request id; response envelope is `{channel,kind:'response',id,ok,result?,error?}`. No direct network, browser control, local-storage credentials, or external assets. The shared Host bridge integration allows management `plugin.call` without a session; `session.summary` / `session.sendMessage` still require a real session. Do not ask the user to create a dummy session. Open sign-in/help/result links via `{method:'plugin.openExternal',url}` on the same channel; Host validates and opens HTTP(S), including self-hosted service URLs. `session.summary` can prefill the current workspace when present; otherwise choose a project directory. Backend panel context only has settings, so send an absolute `project` explicitly for project operations.

All backend actions return `{ok:true,...}` or `{ok:false,error:{code,message,recovery}}`; transport errors remain bridge errors. Use textContent, never render supplier output as HTML. Tokens are write-only password inputs. Clear them after save; response never contains them.

## Actions

- `state {}` -> `{catalog,connections,targets,jobs,guidance}`. Catalog items have `id,label,kind:'code'|'deploy',authModes,cli,fields,docs,notes`. Each field has `key,label,required,type:'string'|'boolean'`; targets expose only non-secret values. Connections have `id,service,label,enabled,authMode:'cli'|'token',baseUrl?,cliPath?,accountId?,username?,hasToken,auth:{state,message,checkedAt?}`. Jobs have `id,kind,connectionId?,targetId?,state,createdAt,result?,error?,loginUrl?,deviceCode?`.
- `save_connection {connection:{id?,service,label?,enabled,authMode,baseUrl?,cliPath?,accountId?,username?},token?,clearToken?}` -> `{connection}`. Service cannot change for an existing id; save token only for token auth. CLI mode consumes that official CLI's normal local login, not a secret scan.
- `remove_connection {id}` -> `{removed:true}`; rejects referenced connections. `set_enabled {id,enabled}` -> `{connection,guidance}`. Disabling immediately removes related operations from guidance and rejects new calls; active cloud work is not undone.
- `check_auth {id}` -> `{auth}`; valid / not_logged_in / expired / offline / missing_cli / error. A failed network check does not erase credentials.
- `install_cli {id}` -> `{job}` for catalog `installable:{package,version,entry}` services (Vercel62.2.0, Netlify27.10.0, Wrangler4.147.0). Label this explicit action Download CLI; it downloads the fixed official npm package into Sites private data, `--ignore-scripts`, never globally, then saves cliPath automatically. Poll `job`; success is `completed`, no extra path editing needed. Other CLI services use an already installed official executable and optional cliPath. Show this action on missing_cli and as optional setup, not on token-only API services.
- `login {id}` -> `{job}`. Only CLI mode with a real upstream login command supports browser/device login. Poll `job {id}` every 2–3 seconds while pending. No developer OAuth registration is needed because the official CLI owns the flow. Token-only services show their docs/account settings, not a fake login button.
- `cancel_job {id}` -> `{job}`; stops local process/wait. A cloud submission may already exist; no auto retry. `job {id}` -> `{job}`. Completed results survive restarts; interrupted remote submissions become `unknown`, interrupted login becomes `interrupted`.
- `repositories {id,owner?,page?}` -> `{repositories,nextPage}`. Code connections only, read-only, page size 30. Entries have `id,name,url,cloneUrl,private`; owner selects GitHub org / Gitea owner / Gitee owner / Bitbucket workspace; GitLab returns membership projects.
- `save_target {target:{id?,service,connectionId,label?,project,...fields}}` -> `{target}`. project is an absolute directory. Catalog fields define service-specific form controls. Targets and connections are distinct entities; GitHub connected is not a deployment.
- `remove_target {id}` -> `{removed:true}`.
- `preview {id}` -> `{preview}` with `id,targetId,project,service,mode,source,command?,request?,warnings,createdAt`. CLI previews show a token-free executable/argv and local configuration filenames. Official CLI owns upload selection, ignore rules and build behavior; this is an operation preview, not an exact file manifest. API targets explicitly say existing remote repository/service source, no local upload. Nothing is sent by preview. Target/config changes require a fresh preview.
- `deploy {previewId}` or `deploy {id:targetId}` -> `{job}`; executes the preview snapshot or creates the necessary preview inline, then checks connection is enabled/auth usable. Selecting a target should auto-load/show its preview in-place; do not force an extra Preview button or second confirmation. Poll `job`. API submissions return accepted remote id/status and only report `ready` after verified provider status. CLI success without deployment URL remains `submitted` or `completed_without_url`, never a fabricated URL.
- `deployment_status {jobId}` -> `{job}` for API targets with status polling. CLI-based jobs already wait for the official tool where supported. A URL with `submitted` is a candidate, not proof the site is live.
- `guidance {}` -> `{guidance}` containing only enabled service operations; no full vendor prompt is globally injected.

## Flow and states

Separate Code connections and Deployment targets. First save connection, check or login, then select/create deployment target with its required identifiers. Show what will be sent, build/upload/config side effects and billing warning from preview, then normal Deploy action (no second plugin confirmation). Show remote acceptance separately from ready URL. Offer Retry check / Sign in again / Edit target based on error recovery. Cancellation or network loss after submission must say result may be unknown and must not automatically upload again. A disabled service stays configured for re-enable but is absent from available guidance.

Backend private data uses server `KIKI_HOME/plugin-data/kiki-sites/` when KIKI_HOME is set, otherwise the normal server-user Kiki home; absolute plugin setting `dataDirectory` overrides it. Render submission polling runs inside the job automatically; job responses expose the accepted remoteId while waiting, and `deployment_status` is a recovery/status refresh rather than a required continuation click. Public docs must state plaintext API tokens protected by normal user filesystem permissions, official CLI/keychain credentials not copied, and disabling/removing does not revoke credentials or delete cloud resources.
